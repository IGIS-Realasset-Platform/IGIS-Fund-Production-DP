# 비용 합치기: 범위·원금액 보존과 연결 검수

2026-10-29 작성. `UI130-04`·`QA130-06`에 연결된 결함 교정입니다. 최신 기능·출력 검수 대상은 **C91**입니다. 실제 운영 DB를 바꾸지 않고 격리된 자료·Edge·모형 HTTP 저장으로 검사했습니다. 정식 배포 사실은 [버전 기록](../VERSION_HISTORY.md)을 따르며 이 문서는 전체 비용관리·플랫폼 전수 완료를 선언하지 않습니다.

## 문제와 수정 범위

같은 비용유형이지만 서로 독립된 1,000,001원과 2,000,000원을 합칠 때 총액이 3,000,001원으로 유지돼야 했습니다. C86 실제 메뉴에서는 이 동작이 두 화면 크기 모두 실패했습니다. 원래 예산 범위가 없던 원자료를 다른 관리항목 아래로 옮기면서 상대의 명시 범위를 상속했고, 합계 검사가 이를 같은 예산의 중복으로 판단했습니다. 총액 검사는 오류를 숨기지 않고 원복했으므로 이 검사를 제거하지 않았습니다.

- 합치기 직전의 유효 범위 또는 범위 부재를 내부 `mergedBudgetScopeRef`로 보존합니다. 기존 상위에서 상속한 범위와 하위의 별도 명시 범위를 구별합니다. 모르는 범위 ID를 새로 만들지 않습니다.
- 명시적으로 같은 예산인 실제 중복은 합치기로 감추지 않습니다. 이미 중복이라 총액이 `null`인 경우에도 `null === null`만으로 합치기를 허용하지 않습니다.
- 양쪽의 원자료 ID 집합을 `mergedSourceIds`로 보존합니다. 원금액·원래 ID·코드·명칭·VAT 기록·계약 배부·과거 보관본을 바꾸지 않고, 각 원래 범위의 현재 금액을 다시 읽습니다. 옛 금액을 상수로 고정하지 않으므로 실제 후속 변경은 해당 VAT 원천에만 반영됩니다.
- 원자료 집합 키 부재, 명시 빈집합의 미입력, 확인된 0원, 일부 미입력을 구별합니다. 합쳐 들어온 다른 원가를 원래 미입력인 VAT 원천의 금액으로 채우지 않습니다.
- 자동 계산 상위를 그 하위 입력과 별개의 중복 비용으로 비교하지 않습니다. 같은 예산의 다른 독립 입력을 차단하는 검사는 유지합니다.
- 원자료 복사 코드의 `method`·`reason`을 호출 인자에도 명시합니다. 기존 원행의 분류 연결을 통째로 전달하면 `assignment()`가 원래 `selected` 값을 우선하여 새 복사 경로가 식별되지 않는 호출 계약 모순을 교정했습니다. 원행의 연결 정보는 그대로입니다.

화면에 새 코드·범위 입력칸·설명표를 추가하지 않았습니다. 회사 비용분류, 금액 계산 방식, 대출·계약·VAT 계산, 기존 확정총액 정책과 다른 서비스·스키마는 변경하지 않습니다.

## 기존 하위 내역의 무효 합치기 차단

기존 명시 분해의 하위 `parentId`만 이동하면 `breakdownParentId`는 삭제된 이전 부모를 가리켰습니다. 클라이언트 총액은 같아도 실제 중앙 검증은 `422 INVALID_COST_BREAKDOWN`을 반환했습니다.

C89는 source 또는 target에 `costBreakdown`·`breakdownParentId`가 있으면 합치기 전에 차단합니다. 해당 동작을 관리 메뉴에서 표시하지 않고 목적지 선택에서도 제외합니다. 직접 호출에는 기존 오류 자리에서 **“하위 내역을 구성한 항목은 합칠 수 없습니다.”**를 표시합니다. 원장·감사·저장 요청 이전에 차단하며 기존 분해 원문을 바꾸지 않습니다. 서버에서 성공할 수 없던 손상 경로를 정상 동작처럼 제공하지 않도록 한 제한이며, 분해의 부모 구조를 재설계하거나 중첩 구조를 새로 만들지 않았습니다. 일반 단순 하위 원자료와 미분해 원가의 합치기는 유지합니다.

## C90 상속 호출과 서버 교정

같은 `assignment()` 계약을 쓰는 생성 경로를 함께 대조했습니다. `addTypedDetail`, 기존 공개 `splitManagementDetail`·`split`, 단순 하위 `merge`, 현행 `costBreakdown.append`에서 새 작업의 raw `method`·`reason`만 명시합니다. 원형 binding의 타입·코드·버전·기록과 전역 assignment 우선순위는 바꾸지 않습니다. 신규 선택을 `allowSystem:false`로 연결할 때는 API가 요구하는 검증된 `costTypeId` 문자열을 전달합니다.

현재 `cbs-split` 버튼은 현행 하위 구성 manager로 연결됩니다. 옛 공개 분해 API의 시험을 이 버튼의 실제 동작으로 세지 않았습니다. 현행 manager의 직접/목록/합계 확인 callback2와 옛 공개 도메인 API를 구분했습니다. 공란·같은 금액 no-op·0/null·연결계약 차단·실패 원복과 원금액/과거/VAT 보존을 유지했습니다. 초기에 옛 폼 제목을 기대한 준비 오류는 유효한 모델 실패와 분리했습니다.

서버는 신규 legacy 비용의 일반 등록을 허용한 것이 아닙니다. 기존 원본의 정확한 복사·변경되지 않은 금액·코드·실제 합치기 계보·접근권한을 확인한 경로만 인정합니다. 서버 담당의 `7f9c…03ff` 단계116/116에는 모형 handler8이 포함되고, 같은 단계14묶음351에는 일부 프런트 검사가 포함되므로 별도로 더하지 않습니다. 이후 서버 `1f7c…aad7`과 최종 C91 클라이언트에서 독립4파일 **68/68·소스변경0**을 다시 확인했습니다. 이는26+7+22+13의 모델/API 검사 수이며 고유 화면 수가 아닙니다.

## C91 실제 Excel의 과거 원자료 누락 교정

C90에서 실제 다운로드한 정상 원자료 파일은 전체·부모·현재 자식 금액은 맞았지만 자식의 과거1,000,001/2,000,000원이 null이었습니다. 동시에 내려받은0/null 파일은 통과했습니다. 이 **1실패/1통과의 원본 파일과 독립 판독**을 보존했습니다.

원인은 `cost-company-profile.amountInfo()`의 실제 복사행이 새 ID만 과거 표에서 찾고, 이미 있는 원래 ID 연결을 사용하지 않던 경계였습니다. C91은 다음 조건으로 과거 조회만 보완합니다.

- 같은 copy ID가 과거에 있으면 그 값이 null/0이어도 그대로 우선합니다.
- copy ID가 없을 때만 정확한 origin ID1개의 범위를 읽습니다. `sourceIds`의 상세와 origin의 소계를 함께 더하지 않습니다.
- 다른 프로젝트의 확인된 owner는 명확히 거절합니다. 같은/빈 stage ID만으로 귀속을 결정하지 않습니다. 실제 WeakMap owner 또는 현재 프로젝트에 담긴 정확한 객체 참조만 표시용 clone에 이어줍니다. 등록 전 snapshot도 원제작자가 확인되면 사용할 수 있습니다.
