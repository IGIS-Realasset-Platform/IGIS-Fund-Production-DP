# v0.11.2 가입·비밀번호 로그인·실제 검수

기준일: 2026-10-16. 최신 직접 요청으로 v0.11.1의 매번 이메일번호 로그인 정책을 대체합니다. 아직 구현/검수 완료 기록이 아니라 이번 작업의 수용기준입니다.

## 승인 범위와 보존

- 최초 가입은 비밀번호 설정과 이메일6자리 소유확인 후 완료합니다. 이후 일반 로그인은 이메일·비밀번호이며 매번 번호를 발송하지 않습니다.
- 사용자가 지정한 회사메일12개만 가입을 허용합니다. 명단은 서버전용 설정으로 관리하고 브라우저·Git·공개문서에 원문을 넣지 않습니다. 도메인 검사만으로 가입을 허용하지 않습니다.
- 기존 OTP-only 본인 계정은 이메일 확인 후 최초 비밀번호를 한 번 설정합니다. 같은 계정ID·최초관리자·권한·A/B/C와 업무자료를 보존합니다. 이미 비밀번호가 있는 계정을 최초설정 흐름으로 덮어쓰지 않습니다.
- 기존 Supabase 프로젝트의 `development_project_platform`만 사용합니다. 공유 Auth·기존 조직 서비스·다른 스키마·기존 비밀값·다른 서비스 보호는 변경하지 않습니다.
- 로그인 이전에는 사이드바·업무메뉴·업무 상단바를 보여주지 않습니다. Lazyweb의 데스크톱 로그인 사례를 조사해 단독 로그인 화면만 수정합니다. 인증 후 기존 업무 UI는 유지합니다.
- 실제 검수는 별도 검수 프로필에서 A/B/C의 승인된 예시자료만 대상으로 합니다. 수정 전 값을 기록하고 시험값은 원복합니다. 다른 사람의 실제 자료·쿠키를 임의 변경하거나 옮기지 않습니다.

## 실행 순서

현재 구조와 원본/보호상태 확인 → Lazyweb/공식 인증문서 조사 → 독립 기대·실패검사 → 서버/화면 병렬 최소수정 → 전체 영향검사 → 전용 Preview설정·게시 → 실제 인증/비밀번호 설정은 본인이 안전한 화면에 입력 → A/B/C 실제 브라우저·DB 검수 → 문서·엑셀·버전기록 동기화입니다.

비밀번호 정책·구체 API 계약은 현재 설치된 Better Auth1.7.8의 실제 인터페이스와 검증으로 확정합니다. 계정 암호를 에이전트가 임의 생성하거나 대화로 받지 않습니다. 실제 확인에 본인 입력이 필요한 단계에서는 미완료를 숨기지 않고 해당 화면의 최소 행동만 안내합니다.

## 확정 API와 정책

- POST `/api/auth-login`: `{email,password}`, 기존 가입자의 비밀번호 로그인. 성공200 identity/HTTPOnly 세션, 틀린 값401 `INVALID_CREDENTIALS`, 메일전송0.
- POST `/api/auth-code`: `{email}`, 신규 또는 비밀번호가 없는 기존 계정의 최초설정만202 `{sent:true}`. 이미 비밀번호가 있으면409 `PASSWORD_ALREADY_SET`·메일전송0.
- POST `/api/auth-verify`: `{email,code,password}`, 소유확인→server-only 최초 setPassword→동일 계정의 세션을 한 트랜잭션에서 저장하고 COMMIT 뒤 응답합니다. 이미 비밀번호가 있으면 덮어쓰지 않습니다.
- 서버 `DP_ALLOWED_EMAILS`는 사용자 지정12개를 Secret으로 관리합니다. 설정 없음/잘못된 목록은 허용으로 fallback하지 않습니다. 현재 세션도 목록을 다시 확인하며 제외된 계정의 로그아웃은 허용합니다.
- 비밀번호는12~128자, 조합강제·trim 없음. 라이브러리 scrypt 해시를 저장하고 평문은 요청 처리 중에만 사용합니다. 가입 단계의 필요한 값은 짧은 비공개 휘발성 상태로만 유지하고 화면/오류복구·취소 경계에서 정리합니다.
- 실제 DB는 기존 전용schema/app_account.password를 사용하며 신규DDL0입니다. 공유 Supabase Auth는 사용하지 않습니다.

## 현재 실행 근거와 미완료

- 독립 합성/모델115개·소스불변, 동일시각 재발송40/40, 실제 전용PG의 합성계정11개·전체원복 통과. 과거 단회검사에서 놓친 재발송 경쟁은 고정시각 반례7개로 보완했습니다.
- 실제 Edge 1280×800/1440×900/1600×1000/390×844에서 새 폼의 배치·가입/코드/취소·비밀번호 비지속·키보드 경로를 검수합니다. 합성 HTTP와 실제 배포 URL 검수는 별도 증거로 구분합니다.
- 게시82eb7ea/HTML `fbe77c99ac29d28ad277c76ec128e28d1053c48ad4128b5232fab52bf3d039ac`의 실제 URL에서 A/B/C 모두 같은셀 입력→+1원 실저장→새 브라우저컨텍스트 재접속→원복을 확인했고 revision2→8입니다. 테스트 수정이력은 남기며 시험금액은 모두 복구했습니다.
- 실제 미허용 주소 요청403과 회원/인증번호 기록0을 확인했습니다. 오류 후 일반 입력의 접근성 이름 교정은 후속 검수 중입니다.
- 본인 비밀번호 설정·이메일 인증·이후 실제 비밀번호 재로그인은 사용자 화면 입력을 기다립니다. 허가되지 않은 임시 비밀번호를 대신 만들지 않습니다.
- 직원 Vercel 계정 장벽 제거는 정식 주소만 공개하고 기존 Preview를 보호하는 방식을 질문했습니다. 답변 전 보호를 전역 해제하거나 다른 서비스를 바꾸지 않습니다.
