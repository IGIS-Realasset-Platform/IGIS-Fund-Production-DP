# 법령 자동수집 부분실패 복구

2026-10-29 추가 관측입니다. [승인 명세](review130-law-collection-recovery-spec.md) · [소스·검사 지문](review130-law-collection-recovery-verification.json). 기존 법령표·비교팝업과 별도 서버 수정이며, 사용자 화면에 운영상태나 새 설명 패널을 추가하지 않습니다.

## 실제 원인

08시 정규 실행은376개 중162개 확인,09시 복구 실행은310개 확인에서 각각 약181초에 끝났습니다. 첫 성공162개를 두 번째에도 모두 다시 조회했습니다. 이전 실패목록은 공급자의 대기시간 확인에만 사용했고, 완료된 진행을 이어받지 않았습니다.

09시 실패66개는 JSON API40423개와 처리시간 예산43개였습니다.08시40417개는09시에 전부 성공해 같은404 집합은0개입니다. 이 관측으로 모든404가 일시적이라고 단정하지는 않습니다. 닫힌 공식 JSON API에서 한 번만 짧게 재시도하고, 다시404이면 실패로 보존합니다. 첨부파일404는 기존1회 실패 정책을 유지합니다.401/403은 반복하지 않고, 빈 응답·없는 ID를 성공0건으로 바꾸지 않습니다.

이전195개 범위의 마지막 성공을376개 성공으로 승계하지 않습니다. 최신 snapshot311개도 오늘 확인된310개와 과거 보존분을 합친 수치입니다. **현재 관측한 자연 실행은 아직376개 전체 성공이 아닙니다.**

## 완료분의 재사용 기준

같은 한국 날짜, 정확한 관리목록 전체와 원자료 식별·원문 지문이 일치할 때만 완료분을 재사용합니다. 체크포인트는 기존 전용 DB의 `reference_snapshots` 안에서 원래 기록·변경이력과 함께 저장됩니다. 별도 테이블·권한·공용 로그인 설정을 만들지 않습니다.

- 전체 범위는 ID·이름·종류·관할·source의 정확한 지문으로 묶습니다.
- 완료 ID는 유일해야 하며, 저장된 전체 record 지문과 실제 공식 계보·현재/예정 판본·공식 링크·원문 해시·그 날짜의 본문 확인시각을 대조합니다.
- 옛 부분결과의 전환은 같은 `attemptedDate`, 실패 ID의 정확한 나머지 집합과 동일 원자료·판본 확인이 모두 증명될 때만 허용합니다. 근거가 부족하면 새 조회를 수행합니다.
- 날짜나 관리범위가 바뀌면 오늘의 새 조회를 시작합니다. 누락기간의 `recoveryFrom`은 마지막 전체 성공 기준으로 남겨 두며, 전날 완료를 오늘 완료처럼 재사용하지 않습니다.
- 오늘 전체 성공이 있었어도 상태 문구만으로 다음 조회를 생략하지 않습니다. 시작 전 현재 관리범위·완료범위·날짜·전체 확인수를 대조해 같을 때만 생략합니다. 같은 날 새 법령 등록·범위 변경은 다음 기존 회차에서 새 조회하고, 프로젝트 연결만 달라진 경우에는 글로벌 관리범위를 바꾸지 않습니다.
- 재사용한 기록의 확인시각을 새로 만들거나 같은 변경 사건을 다시 생성하지 않습니다. 비활성 원문·실패한 대상의 이전 기록·변경이력도 삭제하지 않습니다.

관리대상 전체 수, 이번에 새로 확인한 수, 검증된 재사용 수를 구분합니다. `새 확인+재사용=전체 확인`, `실패=관리대상-전체 확인`이어야 합니다. 실제 HTTP 재시도는 같은 법령 하나의 확인 분모를 늘리지 않습니다.

## 중단·경쟁·재시도

같은 회차의 즉시 연타는60초 동안 막고 한 회차는 최대4번 시도합니다. 이후 포기하는 대신 다음 기존 예약 회차가 검증된 잔여 진행을 이어받습니다. 공급자의 `Retry-After`가 더 길면 해당 시간을 먼저 지키며,404의 표현 가능한 범위를 넘는 대기값도 다음 회차에서 유지합니다. 전체 시간예산에는 체크포인트 검증 시간도 포함합니다. 무한 서버 대기나 인증 실패의 무한 재시도를 하지 않습니다.

기존 실행잠금과 소유자 대조를 유지하고, 저장 직전에 한국 날짜·현재 관리범위를 다시 확인합니다. 법령 등록과 수집 결과 저장은 같은 짧은 범위 잠금을 공유하며, 네트워크 조회 중 DB 잠금을 유지하지 않습니다. 원문·체크포인트·수집상태는 같은 거래에서 저장되므로 정상 정규 실행에서도 중간 저장 실패가 일부 완료만 남기지 않습니다. 직접 관리자 SQL은 이 잠금을 우회할 수 있으므로 별도 순차 조율이 필요합니다.

## 검증 범위

새 수집기42개, 예약 실행28개 반례를 포함한32묶음524검사가 통과했습니다. 날짜·범위·원문 hash를 맞춘 뒤 조작한 계보/판본 반례,0/null, 부분 결과 재개, 동일 사건 보존,60초 경계,4회 이후 다음 회차, 날짜 변경, 실행 소유자 교체와 저장 실패를 검사했습니다. 최종 공유잠금을 기다리는 동안 자정이 되는 반례도19통과/1실패로 먼저 재현한 뒤, 잠금 후 저장 직전 날짜를 한 번 더 대조해 교정했습니다.

독립 검토에서 오늘 성공 이후 범위가 바뀌어도 시작 전 건너뛰던5개 반례,404의 큰 대기값을 다음 회차에서 잃던1개 반례를 추가로 재현·교정했습니다. 프로젝트 연결만 바뀐 경우의 기존 조회 생략은 보존합니다. 체크포인트 검증 시간을 뺀 뒤 예산을 시작하던 경계도41통과/1실패에서 재현해 전체 예산에 포함했습니다.

구식 메모리 DB에는 정확한 새 잠금 문장과 인자만 추가했습니다. 정상 수집 목업이 생략했던 날짜·대상 수를 실제1개 대상의 독립 값으로 보완했으며, 권한·원문·실패·이전 값 보존 검사는 유지했습니다. 첨부404까지 넓어진 초기 교정은 회귀검사에서 발견해 공식 JSON API에만 좁혔습니다.

이는 로컬·명시적 메모리 검사입니다. 새 코드 배포와 실제 잔여 복구의 `fresh/reused/checked`·DB 결과는 root가 별도로 확인해야 합니다. 이 문서로 실제376개 복구 성공을 미리 체크하지 않습니다.
