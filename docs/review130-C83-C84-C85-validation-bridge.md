# REVIEW130 · 버전·검수 단위 분리

최종 후보 C85는 6,870,565바이트이며 SHA-256은 `86b47fef5c5d77efb87c6bcec19ac8ed22d743ac21616de4ee618050725585a5`입니다. C84와 C83의 검수 결과를 같은 HTML에서 한 번 실행한 결과로 합치지 않습니다. 파일·부분 함수별 실제 포함 지문은 동일 이름의 JSON에서 확인할 수 있습니다.

## C84 → C85

C84에서 확인한 비용 입력·보증기관·최초 날짜폭·경로 없는 분류에 쓰이는 core/CBS/계약/분류/하위분해/인허가 모듈과 관련 CSS의 현재 전체 소스가 C84·C85에 모두 정확히 포함됩니다. 따라서 다음은 **C84의 실제 실행 + C85의 해당 소비자 소스 동등성**으로 연결합니다.

| 단위 | C84 실제 수행 | C85 연결 |
|---|---:|---|
| 비용 하위입력 업무 흐름 | 2/2 | 같은 비용·폼·계산/저장 소비자 소스 |
| 보증기관 필드 문맥 | 10/10 | 같은 계약·core·보존된 상위 펼침 처리 |
| 최초 날짜 조회 표/해상도 | 10/10 | 같은 표 생성·최초 fit·CSS |
| 경로 없는 분류 업무 흐름 | 4/4 | 같은 분류·폼·원금액 보존 소비자 |

이 네 단위는 서로 다릅니다. 이를 더해 플랫폼의 고유 기능 수라고 부르지 않습니다. C85의 알림 팝업, 보고서 아카이브/최근 제출, 소유자 명세 변경은 이 수락 범위에 들어 있지 않으며 별도 담당자의 실제 검수로 확인합니다. 사이드바 알림 요약의 `sidebar`·`updateSidebar` 부분 함수는 C83·C84·C85가 같지만 이것이 알림 팝업의 동등성을 뜻하지 않습니다.

## C83 → C85

`A.editable`, 입력 열 고정·해제, 가시 위치 보정, 편집 시작·저장·취소·클릭, 기본 형식 해석 등 부분 함수는 C83·C84·C85에서 정확히 같습니다. `A.table`·`tableMetrics`도 같지만 개별 셀의 최소폭을 측정하는 `tableCellMinimum`은 C84에서 달라졌으므로 분리합니다. C84에는 **최초 폭 fit·상위 펼침 보존·명시적인 폼 초안 소비**, 뒤에는 **overview의 보고 아카이브 조회/최근 제출**도 추가됐습니다. 따라서 C83 전체 실행을 C85 전체 실행 통과로 바꾸지 않습니다.

C83의 실제 분모는 다음과 같이 구분합니다.

| 분모 | 발견/수행 | 결과·한계 |
|---|---:|---|

보증기관의 준비차단 10개는 후속 C83에서 실제 상위 펼침 손실 10실패로 확정했고 C84의 같은 10개 문맥에서 해결했습니다. 이로써 기존 공백은 구체적으로 연결하되 다른 555개를 C85에서 다시 실행했다고 표시하지 않습니다.

프리셋/CBS/마스터/분류체계/회사표/정렬/코딩, construction의 `permit-views`·`permit.css`, 사용자 유지 지시가 있는 `permit-detail.css`의 전체 소스도 C83·C84·C85에서 같음을 대조했습니다. 관련 `COST_TYPE_MASTER`·`COST_TAXONOMY`·`COST_USE_PRESETS`의 JSON과 과거 3개 마스터 아카이브도 실제 변수 선언의 포함 문자열까지 같습니다. 이는 정의·소비자 보존 증거입니다. 후속 C85 정확본의 construction33/5폭 5통과, owner 업무10통과, 혼합 코드2통과와 실제 Excel4개 읽기 결과는 `review130-frontend-native-C85.md`에 별도로 기록했습니다.

검수 그룹 수, 업무 흐름 수, 필드 문맥 수, 물리적 입력 UI 수는 다른 단위입니다. 새 검사 결과를 기록할 때 해당 단위와 실행한 정확한 HTML 지문을 먼저 붙이며, 하나의 `574개 기능 통과` 같은 합계로 묶지 않습니다. 실제 DB 쓰기는 본 담당자 기준 0회입니다.
