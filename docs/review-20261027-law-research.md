- 요청: 앱에서 공식 법령·행정규칙·전국 자치법규를 검색하고, 결과의 추가 버튼으로 관리 법령/기존 일일 확인 체계에 편입한다.
- 기준: 국가법령정보 공동활용 [시행일 법령 목록](https://open.law.go.kr/LSO/openApi/guideList.do), [행정규칙 목록](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=admrulListGuide), [자치법규 목록](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=ordinListGuide), 2026-10-27 열람. 목록 API는 이름 검색·20건 기본·최대100건·page를 지원하며 지역 org/sborg는 선택 조건이다. 전국 검색에는 이를 보내지 않는다.
- 기존 서버: `/api/law-search`는 공식 검색을 수행하지만 프로젝트가 필수이고 첫20건만 제공한다. `/api/law-watch`는 공식 본문·권한을 재확인하고 기존 전용 스키마의 공용 `law_watchlist`와 사업별 `law_project_watches`에 원자적으로 저장한다. 예약 수집은 active 공용목록을 읽으므로 새 스키마/예약 추가가 필요하지 않다.
- 확인한 결함: 검색 탭은 API를 호출하지 않고 공식 사이트만 연다. 관리표는 수집 완료 스냅샷만 사용하여 새로 추가한 관리법령이 다음 수집 전에는 보이지 않는다. 검색 API에는 다음 페이지가 없다.
- 최소 변경: 검색 탭을 API 결과표로 연결하고 페이지 이동을 제공한다. 조회는 인증 상태에서 사업 없이도 허용하지만 추가는 현재 사업 편집권한과 공식 본문 검증을 그대로 사용한다. 관리목록에는 실제 DB watch의 공식 식별정보만 합치며 미확인 금액·날짜·법적 적용을 만들지 않는다.
- 보존: 기존 사업별/인허가 검색 팝업 부모복귀·본문/신구대비 조회·원장/법적판단·사용자 기록·기존 예약/법령수집·기존 서비스/다른 스키마.
- 독립 기대/반례: target3·첫/다음 페이지·0건·공급자 실패·누락/중복 페이지·사업0·viewer·권한회수·동시중복·다른 사업 전환·검색조건 변경·늦은 응답·같은 이름 다른 공식ID/관할·새 관리항목 즉시표시·원장 불변. 실제 DB/공식 응답과 격리 모의를 별도로 기록한다.
- 실패검사: 변경 전 신규5기대 중4실패(앱검색영역 없음, project 없는 조회403, 다음페이지 미지원, 수집 전 새 관리항목 미표시), 입력차단1통과를 확인했다. 첫 구현17/17 후 독립검토가 연결 반례3개를 추가 발견했다. 이를 새 실패검사로 고정하고 교정한 C63은20/20 통과했다. 모듈/준비 오류를 제품 RED로 세지 않았다.

## 독립 반례 교정과 C63 실제 격리 브라우저

- 독립 검토자가 구현자와 다른 fixture/기대로 발견한3개는 첫 구현의 결함이다. ① 추가 전 시작된 늦은 관리GET이 저장한 신규관리행을 삭제, ② 공용관리와 현재사업 구독을 혼동해 다른 사업의 명시적 연결을 막음, ③ 다음페이지 로딩·실패에서 이전행 버튼 표시와 실제 실행 조건이 불일치했다.
- 확정 POST의 화면 반영은 해당 관리ID와 사업연결이 서버 재조회에 확인될 때까지 유지하고, 진행 중 관리GET 뒤 강제 재조회가 이어지게 했다. 새 DB 구조·권한을 만들지 않았다.
- 공용관리에 있으나 현재사업에 미연결이면 `사업에 연결`을 제공한다. 같은 사업에 이미 연결된 경우 `관리 중`이다. 클릭 없이 다른 사업의 구독을 생성하지 않는다.
- 다음페이지 로딩 중 이전행 추가를 비활성화하고, 실패 후 유지된 이전 페이지의 행은 실제 추가할 수 있게 했다. 독립 원fixture SHA `ec909e3cc27976ec639fc98a83054029647b541191d818a0483d6f685e6b06f3`의 기대를 바꾸지 않고 독립 재검토3/3 통과했다.

## 최종 C64 — URL 경계와 좁은 결과표 교정

C63 검수 뒤의 추가 검토도 보존한다. 전체 회귀의 구식 DTO 기대와 별도로, 공식 LSW 경로의 legacy `source.url`에 `OC` 이외의 임의 query/hash가 있으면 기존 fallback이 이를 보존하는 경계를 발견했다. 실제 인증값은 읽지 않았으며 `synthetic-private`만 넣은 독립 모의로 재현했다. 신규 실패검사를 먼저 기록한 뒤, 대상별 공식 경로·단 하나의 숫자 판본ID만 해석하고 URL을 새로 구성하도록 교정했다. 종류가 다르거나 explicit sequence와 URL의 ID가 다르거나 ID query가 중복되면 공개 식별정보를 null로 두며 이름으로 대체하지 않는다.

- 최종 신규 논리검사 **21/21**. `source` 공개키는 `sequence`, `lawId`, `url` 3개뿐이다. 값이 없는 기존 QA행의 독립 예상 DTO는 `{target:'law',name:'QA 법령',jurisdiction:null,status:'configured',source:{sequence:null,lawId:null,url:null}}`이다. 법령 records·개정·첨부·날짜·기존 무쓰기 검사는 그대로 유지한다.
- 서버 SHA `97283af2376396a6118da35d20c146308c4cfb1e82a623cc5ba4f6d6540cedca`; 법령JS는 C63과 같은 `db48a83962f24284531950318dc0d30f3de9b84acf44b9436b8e806abc4905c1`이다.
